# Verse v1 plan

Goal: build the Verse v1 meeting assistant so that the speed targets in spec section 6 are met and measured.
Spec: `docs/specs/2026-10-14-verse-meeting-assistant-v1-design.md` (approved by Alex 2026-10-14); critique:
`docs/specs/2026-10-14-speed-critique.md`.
Approach: Phase 0 measures the four unknowns that can change the design (API latency, speech latency, Brave
audio capture, rate limits), with throwaway CLIs. Only after Alex accepts the numbers does Phase 1 build the app
(Swift + Python brain). The Phase 1 packages are fixed in scope and order now; their test cases and thresholds
are finalised from the Phase 0 results.

Global constraints (verbatim from the spec):
- Models: `claude-haiku-5-5` (S/F: effort low, thinking disabled) and `claude-sonnet-5-5` (D: effort medium,
  thinking `between_tools` unless measured otherwise). Prep runs on `claude-sonnet-5-5` at effort high.
- Paid only from the Max monthly API credit: an API key from "Personal API Org", read from the Keychain item
  `verse-anthropic` (account = `$USER`). Never print, log or write the key. No Claude.ai/Max OAuth.
- Python: official `anthropic` SDK ≥ 1.13 (pinned in `requirements.txt`) and `httpx[http2]`. No other LLM
  provider.
- No audio file is ever written. Measurements store numbers only (timings, RMS, transcripts of synthetic test
  audio).
- t = 0 is the acoustic end of the question; every timing is logged per stage.
- No GUI windows during tests (CLI only); kill every process you start, also on failure (memory
  `feedback-gui-test-windows`).
- macOS 26, Xcode 27, Swift 6. No git commits or pushes without the owner's OK.

Packages: Phase 0 = P0-A, P0-B, P0-C, which run in parallel (disjoint folders). Then a gate: Alex reviews
`bench/RESULTS.md`. Phase 1 = P1-1 … P1-6 (order below).

Checklist:
- [ ] P0-A API latency + rate limits
- [ ] P0-B Speech latency + language availability
- [ ] P0-C Remote-audio capture probe (Brave / Meet)
- [ ] Gate: Alex accepts `bench/RESULTS.md` (spec revised if targets are out of reach)
- [ ] P1-1 … P1-6

## Phase 0: measurements (CLI only, throwaway)

### Package P0-A: API latency and rate limits
Agent: worker-hard
Owns: `bench/api/` (bench_api.py, requirements.txt, README.md, results/*.json), `bench/api/RESULTS_api.md`
Do not touch: `bench/speech/` (P0-B), `bench/audio/` (P0-C)
Read first: spec §5.8 and §6; critique §1 B9–B11 and §3; claude-api skill (Python README, streaming, prompt
caching: pre-warm, TTL, rejected `max_tokens: 0` combinations)

Decisions:
- Use the async client with a custom `httpx.AsyncClient(http2=True, limits=httpx.Limits(keepalive_expiry=300))`.
- Prompt layout per spec §5.8: frozen system → synthetic meeting pack of ~6k tokens (breakpoint 1) → 6
  synthetic finalized turns (breakpoint 2) → the question.
- Output is plain-text lines (`SAY:` / `- `). No structured output.
- Measure from request start to the first text delta (TTFT) and to the first complete `SAY:` line; record the
  server-side `usage` (cache read/write tokens).

Test cases:
- warm_haiku: 30 calls, Haiku, effort low, thinking disabled, cache warm → p50/p90 TTFT; every call after the
  first has `cache_read_input_tokens > 0`.
- cold_haiku: 10 calls after > 6 min idle or with a fresh connection → p50/p90 TTFT and the cold-connection
  delta.
- prewarm: `max_tokens: 0` non-streaming request with the identical tuple → the next real call reads the cache.
- sonnet_between_tools vs sonnet_adaptive: 15 calls each, effort medium → p50/p90 TTFT and to the first point.
- cancel_billing: start a Sonnet stream, close it after the first delta → report `usage.output_tokens` if
  available, and say whether billing stopped (mark unconfirmed if the API gives no evidence).
- rate_limit_headers: read the `anthropic-ratelimit-*` response headers → record the org's limits per model.
- Total spend of the run is printed from `usage` (target < $1).

Acceptance: `cd bench/api && python3 -u bench_api.py --all` → writes `results/api-<timestamp>.json` and prints a
p50/p90 table; the `bench/api/RESULTS_api.md` is filled in from it.
Done means: the table exists for all cases with n as stated, cache reads are proven, and the rate limits are
recorded.
Stop and ask if: the Keychain item `verse-anthropic` is missing or the API returns 401/403 (Alex must create
the key), or spend would exceed $2.

### Package P0-B: Speech recognition latency and languages
Agent: worker-hard
Owns: `bench/speech/` (Swift package `SpeechBench`, fixtures/, results/), `bench/speech/RESULTS_speech.md`
Do not touch: `bench/api/`, `bench/audio/`
Read first: spec §5.4 and §5.7; critique B4 and §4; Apple SpeechAnalyzer / SpeechTranscriber docs
(`bestAvailableAudioFormat`, volatile vs final results, `audioTimeRange`, `supportedLocales` / asset
installation)

Decisions:
- Synthetic test audio is made with `say` in memory or in temp files that are deleted at the end (CLI, no GUI):
  - en_US: Albert;
  - it_IT: Alice and Eddy;
  - tr_TR: Yelda.
  20 questions per language, including Turkish `mı/mi` questions and Italian yes/no questions.
- Synthetic audio files are test fixtures, not meeting audio; delete them after the run and record their deletion.
- Feed audio at real-time pace (not faster) to measure live behaviour.

Test cases:
- locales: list the supported and installed locales; report en_US, it_IT, tr_TR as available, downloadable or
  absent.
- volatile_lag: per language, the delay between a word's audio end time and its first appearance in a volatile
  result → p50/p90.
- final_lag: the delay between the acoustic end of an utterance and the final result → p50/p90.
- word_accuracy: WER of the final result vs the script, per language.
- question_end_cues: whether volatile text carries punctuation (`?`) early enough to use as a cue.

Acceptance: `cd bench/speech && swift run -c release SpeechBench --all` → `results/speech-<ts>.json` and a table;
`bench/speech/RESULTS_speech.md` filled in.
Done means: all three languages are reported (even as "absent"), with the lag tables for those available.
Stop and ask if: SpeechAnalyzer needs a model download that requires a GUI prompt, or tr_TR is absent (report
this and propose whisper.cpp as the Turkish fallback, without installing it).

### Package P0-C: Remote-audio capture probe
Agent: worker-xhard
Owns: `bench/audio/` (Swift package `TapProbe`, results/), `bench/audio/RESULTS_audio.md`
Do not touch: `bench/api/`, `bench/speech/`
Read first: spec §5.7; critique B5, B6; Apple Core Audio process taps (`AudioHardwareCreateProcessTap`,
`CATapDescription`), aggregate devices; ScreenCaptureKit audio-only capture as the fallback

Decisions:
- Primary: a Core Audio process tap on all PIDs of a chosen app (Brave and its helper processes). Fallback:
  ScreenCaptureKit audio for the same app.
- Never write audio. Compute per-100 ms RMS and the peak, and print or save the numbers only.
- Alex plays a YouTube video or joins a test Meet in Brave while the probe runs. The probe needs no window; any
  permission dialog appears for Alex to approve.

Test cases:
- list_targets: list the audio-producing processes and Brave's helper PIDs.
- tap_brave: 20 s tap on Brave's PIDs while audio plays → RMS above the noise floor in ≥ 80 % of windows; silence
  while playback is paused.
- isolation: system sound from another app (e.g. `afplay` of a system sound) → not present in the Brave tap.
- mic_bleed: speakers on, mic open, Brave playing → envelope correlation between the tap and the mic at a
  0–80 ms lag (report the value).
- fallback_sck: if the tap fails, the same test via ScreenCaptureKit.

Acceptance: `cd bench/audio && swift run -c release TapProbe --app "Brave Browser" --seconds 20` →
`results/audio-<ts>.json`; `bench/audio/RESULTS_audio.md` filled in with which route works.
Done means: a route that captures Brave's audio is proven, or both routes are shown not to work, with the error.
Stop and ask if: a permission cannot be granted from the CLI context, or the owner's interaction is needed to play
audio (send a short message saying exactly what to click).

- any spec revision needed.

Alex accepts it before Phase 1 starts.

## Phase 1: build (scope and order fixed; tests and thresholds finalised at the gate)

1. **P1-1 Prep stage (Python, worker-hard):** builds the bank, fact sheet, glossary, snippets and meeting pack
   from a prep note, `beyin.py context --no-sync` and `git log`; a review file for Alex.
2. **P1-2 Brain (Python, worker-xhard):** S (≤ 3 in flight), F and D routes, the fixed cache layout, pre-warm,
   keep-alive, token bucket, the text-line protocol over stdin/stdout, and the `OPENER_OK/WRONG` and `BANK:`
   handling.
3. **P1-3 Audio + transcriber (Swift, worker-xhard):** the route chosen in P0-C, mic with voice processing and
   bleed gate, SpeechAnalyzer streaming of volatile partials.
4. **P1-4 Turn logic (Swift, worker-hard):** predictive endpointing with language cues, addressee detection,
   the matcher (n-gram TF-IDF, plus embeddings where useful) and fact chips.
5. **P1-5 Overlay + app shell (SwiftUI, worker-hard, `frontend-developer` skill):** the Liquid Glass notch
   panel per spec §5.9, settings, Keychain, brain process supervision.
6. **P1-6 Replay harness + eval (worker-hard):** 2- and 3-speaker synthetic dialogues, a blind paraphrase set,
   per-stage latency logs, and the spec §9 acceptance report.

P1-1 and P1-3 can run in parallel. P1-2 needs P1-1's pack format. P1-4 needs P1-3. P1-5 needs P1-2 and P1-4.
P1-6 runs last.
