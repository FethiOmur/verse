# Verse code review, 2026-11-11

Read-only review of the Swift app (`app/Sources`) and the Python brain (`brain/verse_brain`). No code was changed.

How to read this:

- **Proven** means a targeted experiment showed the failure (the command is given). **By reading** means the code path
  was read end to end but not executed. **Not verified** means the trigger depends on hardware or a live condition
  that was not reproduced; where I looked is stated.
- Severity: critical / high / medium / low. Nothing was rated critical: no finding leaks the API key or destroys
  session data on its own.
- Scope read by the reviewer directly: `runtime/engine.py`, `transport.py`, `__main__.py`, `protocol.py`,
  `ratelimit.py`, `settings.py`, `events.py`, `prep/pipeline.py`, `ground.py`, `sources.py`, `model.py`,
  `keychain.py`, `VerseTurns/VerseRunner.swift`, `TurnEngine.swift`, `BrainProcess.swift`, `VerseAudio/ProcessTapSource.swift`,
  `MicSource.swift`, `Permissions.swift`, `CoreAudioSupport.swift`, and the start/stop paths of `VerseUI/VerseController.swift`.
- Speech recognition, meeting detection, the UI stores and session files, and the secondary Python modules were
  read by three delegated sub-reviews. Section 3 says which of their findings I re-checked.

## 1. Findings, most severe first

### H1. One transient API error during pre-warm ends the session before it starts (high, proven)

- `brain/verse_brain/runtime/engine.py:686-712`: the pre-warm loop retries only `Offline` and `asyncio.TimeoutError`.
  `Overloaded` (every 5xx and `overloaded_error`), `RateLimited` and `BadRequest` fall to `except TransportError` at
  line 711, which emits `status error "pre-warm failed: ..."` on the first failure, with no retry and no later `ready`.
- `app/Sources/VerseTurns/VerseRunner.swift:1028`: the first `ready|offline|error|credit_exhausted|rate_limited`
  status becomes the run's `ready` value. `VerseRunner.swift:423-427`: `error` means "brain did not become ready",
  the brain is stopped and the run returns 1. Listening never starts.
- Same path after a mid-call brain restart: `VerseRunner.swift:877-881` calls `failBrain`, which stops the listen
  session (`VerseRunner.swift:862-868`), so the transcript stops too.
- Proof: `VERSE_EVENTS=0 VERSE_SIMULATE_API=overloaded python -u -m verse_brain.runtime --no-embed` with a `start`
  line for `brain/tests/fixtures/runtime/session` prints `warming`, then immediately
  `{"type":"status","state":"error","message":"pre-warm failed: simulated overloaded"}`.
- Note that `offline` is already treated as non-fatal (the run goes on and the ping loop recovers), so a 503 is
  handled worse than having no network at all.
- Fix: pre-warm is an optimization, so it must not decide whether the call runs. In `on_start`, retry `Overloaded`
  and `RateLimited` inside the existing attempt loop (short backoff, honour `retry-after`), and when all attempts
  fail emit a non-fatal state (`ready` with a `degraded` flag, or reuse the offline recovery: keep trying in
  `_keepalive_loop` and send `ready` when a warm call succeeds). In Swift, treat only `no_api_key`,
  `invalid_api_key` and `no_credit` (the `reason` key) as fatal at start.

### H2. The final summary is cut off 3 seconds after Stop (high, proven on real sessions)

- `app/Sources/VerseTurns/BrainProcess.swift:147-155`: `shutdown(grace: 3.0)` sends `control stop`, closes stdin,
  waits 3 s, then SIGTERM, then SIGKILL after 1.5 s. `VerseRunner.swift:410-413` calls it with the default.
- `brain/verse_brain/runtime/engine.py:2238-2251`: `stop()` runs the final Sonnet merge and waits up to
  `final_timeout_s = 45` (`settings.py`). The Python process has no SIGTERM handler, so it dies mid-call.
- Nothing else triggers the merge: `BrainCommand.summarize` is defined in `VerseTurns/Wire.swift:212,232` and never
  sent (grep over `app/Sources`).
- A user Stop also skips `drain()` (`VerseRunner.swift:913-915`, `guard !stop`), so the 3 s grace is all there is.
- Evidence: of the 5 `summary.md` files under `~/Library/Application Support/Verse/sessions`, 4 carry
  `> DRAFT: final merge pending` (213, 237, 269 and 405 turns). The only merged one has 2 turns.
- The money for the merge is still spent on the API side, and the `summary{final:true}` event never reaches the app.
- Fix: give the meeting stop path a grace of `final_timeout_s` plus a margin (50 s), or better, send `summarize`
  first, show "Summarizing…" in the island, and send `stop` when `summary{final}` or a timeout arrives. Keep the
  short grace for Quit, and write a reason into the draft note so a draft can be re-merged later (the app's Ask/brief
  processes could offer "finish summary").

### H3. A write to a dead brain kills the whole app with SIGPIPE (high, proven in isolation)

- `app/Sources/VerseTurns/BrainProcess.swift:134-138`: `send` writes to the child's stdin pipe with
  `try? FileHandle.write(contentsOf:)`. The comment says failures are ignored on purpose, but with SIGPIPE at its
  default disposition the process is terminated before any error is thrown.
- `app/Sources/VerseApp/VerseApp.swift:153-154` ignores only SIGTERM, SIGINT and SIGHUP. `signal(SIGPIPE, SIG_IGN)`
  exists only in the CLI (`app/Sources/verse-run/main.swift:122`).
- Trigger: the brain exits (see H4) while the run loop is sending partials several times a second. Any `send`
  between the child's exit and `brainEnded` flipping the phase (`VerseRunner.swift:829-846`) hits a closed pipe.
  `shutdown()` has the same window between `isRunning` and `send(stop)`.
- Proof: a 15-line Swift program that spawns `/usr/bin/true`, waits for it and writes to its stdin pipe with
  `write(contentsOf:)` exits with status 141 (128 + SIGPIPE) and prints nothing after the write. Not reproduced
  inside the app itself.
- Effect: the supervision in `VerseRunner` (restart once, re-send the question) never gets to run; the meeting
  assistant disappears mid-call.
- Fix: `signal(SIGPIPE, SIG_IGN)` at the top of `applicationDidFinishLaunching` (and in `verse-listen`,
  `verse-meet`), or set `F_SETNOSIGPIPE` on the pipe's write descriptor in `BrainProcess.init`.

### H4. Any exception in a message handler ends the brain; the second one ends the call (high, proven)

- `brain/verse_brain/runtime/__main__.py:172`: `await runtime.handle(msg)` has no `try`. Only JSON and
  message-type errors are caught (lines 137-141). An exception in any synchronous handler path unwinds `amain`.
- Direct indexing in the handlers: `engine.py:1079` (`msg["turn_id"]` in `on_partial`), `engine.py:1258`
  (`on_bank_hit`), `engine.py:1343` (`_on_turn`). The follow path is wrapped (`_follow_safe`); the S/F/D path, the
  room route (`_room_route`, `own.py`) and the embedding callbacks are not.
- Proof: with `--fake`, a `start` line followed by `{"type":"partial","speaker":"remote","text":"..."}` (no
  `turn_id`) gives a `KeyError` traceback and exit status 1.
- Swift restarts the brain once per session (`VerseRunner.swift:837-845`, `restarts == 0`). A second exit sets
  `brainFailed` and stops listening (`failBrain`), so the rest of the meeting is not even transcribed.
- By reading: the restarted brain starts with an empty `turns` list (`engine.py:514`). Cards after a restart have no
  conversation context, and the end-of-call `summary.md` is rewritten from the post-restart turns only
  (`engine.py:2163-2177`).
- Fix: wrap `runtime.handle` in `try/except Exception` that logs, emits a `metric`/`status` and continues. Validate
  `turn_id` once in `parse_line`. In Swift, allow more than one restart (for example 3 with backoff), never stop the
  listen session because the brain failed (keep the transcript), and replay `transcript.jsonl` to a restarted brain
  (a `history` message) before re-sending the question.

### H5. No handling of audio device changes during a call (high, not verified on hardware)

- `app/Sources/VerseAudio/MicSource.swift:37-78`: the `AVAudioEngine` is started once. Nothing observes
  `AVAudioEngineConfigurationChange`; the engine stops itself when the default input or its format changes (AirPods
  connecting or switching to headset mode, a USB mic unplugged). The microphone channel then stays silent until the
  session is restarted.
- `app/Sources/VerseAudio/ProcessTapSource.swift:120-121,164`: the tap's sample rate is read once at creation and
  captured by the IOProc block. There is no listener on `kAudioTapPropertyFormat` or on the default output device.
  If the output device changes to one with another rate, chunks keep being labelled with the old rate.
- `onEnd` is never called by either live source (`MicSource.swift:36`, `ProcessTapSource.swift:73`), so the listen
  session cannot learn that a source died.
- Where I looked: grep for `ConfigurationChange`, `DefaultInputDevice`, `DefaultOutputDevice` and
  `kAudioTapPropertyFormat` over `app/Sources` finds only the `verse-listen` CLI probes
  (`verse-listen/VerseListen.swift:195,209`) and the one read at `ProcessTapSource.swift:120`.
- Not verified: whether the process tap's format really changes with the output device on macOS 26, and how
  `ChannelPipeline` uses `AudioChunk.sampleRate`. Test: start a call, connect AirPods mid-call, watch both channels.
- Fix: observe `AVAudioEngineConfigurationChange` and rebuild the engine (the run already supports an in-place listen
  swap, `VerseRunner.switchListening`); add property listeners for the tap format and the default output device and
  rebuild the tap as `refreshPIDList` already does; report a dead source as an `issue` so the island can show it.

### H6. A non-fatal `status error` in mid-call hides every later card behind the error panel (high, by reading)

- `app/Sources/VerseUI/OverlayState.swift:515` sets `.error`; `:122` makes `.error` a status that needs the panel;
  `app/Sources/VerseUI/IslandViews.swift:79` resolves a needs-panel status ahead of the card.
- Nothing clears it while the call runs: `openCard` clears only `.meMissing` (`OverlayState.swift:604`), `ready`
  clears only offline, rate-limited and restarting (`:507`).
- The brain sends such errors for single calls: `request rejected` and the generic `{kind}: {e}` for D/A or an
  unbuffered F (`brain/verse_brain/runtime/engine.py:1044,1047`). With M3 and M4 that includes one 5xx or one
  dropped connection.
- Effect: after one failed call, cards are still produced but stay invisible until he presses Dismiss, in the
  middle of a conversation. The practice interview has the same path (`OverlayState.swift:942`).
- `rate_limited` has a milder form: the chip is set at `OverlayState.swift:511` and the brain never sends the `ready`
  that would clear it after a 429 (`engine.py:910` is the offline recovery only). Cards stay visible, but the
  "press again to stop" hint is suppressed for the rest of the call (`app/Sources/VerseUI/OverlayModel.swift:66`).
- Fix: show per-call errors as a capsule chip while a session runs (`needsPanel` only when not running), and clear
  `.error`/`.rateLimited` when the next card gets content.

### H7. A Turkish month typed without diacritics or in capitals crashes prep after the model calls are paid (high, proven)

- `brain/verse_brain/prep/conflicts.py:92`: the month alternation is compiled with `re.I`. Python's case-insensitive
  matching treats `i`, `ı`, `I`, `İ` as one letter, so the pattern for `kasım` also matches `kasim` and `KASIM`.
- `conflicts.py:597,600,603` (and `:422,424`) then do `MONTHS[m["mon"].casefold()]`; the table has only the
  diacritic spellings, so the lookup raises `KeyError`.
- `brain/verse_brain/prep/pipeline.py:295` calls `apply_conflicts` unguarded, after every generation call.
- Proof (`brain/.venv/bin/python`): a pattern built from `conflicts.MONTHS` with `re.I` matches `kasim 2026`,
  `3 Aralik 2026` and `MAYIS 2027`, and `m["mon"].casefold() in MONTHS` is `False` for each. The reviewing agent also
  ran the module's own functions and got `KeyError('kasim')`, `'aralik'`, `'mayis'`, `'ni̇san'`.
- Trigger: any line of the prep note, a vault record or a commit subject with such a date.
- Fix: fold before the lookup (ı/İ to i, strip combining marks) or use `MONTHS.get` and skip the match; add the
  ASCII spellings; wrap `apply_conflicts` so a conflict-check failure becomes a warning in `review.md`.

### H8. A recognizer failure during a call is swallowed; the channel goes silent with no signal (high, by reading)

- `app/Sources/VerseSpeech/NemotronEngine.swift:252-257,271-277`: when `manager.process` throws, the error goes into
  `errorSlot` and the run returns. `runError` (`:131`) and `ChannelPipeline.feedError`
  (`ChannelPipeline.swift:22,88,111`) are never read anywhere in `app/Sources` (grep).
- After the switch to Nemotron the Apple engine is already closed (`SwitchingEngine.swift:168`), so nothing takes
  over. The dead-stream watchdog watches audio chunks, which keep arriving, so no `issue` is raised.
- Not verified: how often `process` throws in practice.
- Fix: report engine failures through the session's `issues`, and let `SwitchingEngine` fall back to a fresh Apple
  engine at the point of failure.

### M1. Grounding: a short fragment after an ellipsis is accepted unchecked and then supports a number (medium-high, proven)

- `brain/verse_brain/prep/sources.py:139-140` and `162-165`: a quote is split on `...`/`…` and pieces shorter than
  4 normalized characters are dropped from the check. The stored `Source.quote` is the model's full string.
- `brain/verse_brain/prep/ground.py:71`: `numbers_supported(text, [s.quote ...])` reads numbers from that stored
  string, not from the document.
- Proof (`brain/.venv/bin/python`): with the note line `Revenue grew strongly this year thanks to the new plan.`,
  `book.resolve("prep:L2", "Revenue grew strongly ... 40%")` returns a verified source and
  `numbers_supported("Revenue grew 40% this year", [quote])` is `True`. `40%` is nowhere in the note. With the honest
  quote the same point is rejected.
- Related, by reading: the pieces of an ellipsis quote may come from anywhere in the note in any order
  (`sources.py:149-155` joins all lines), so a number from one section can be attached to a claim from another.
- Fix: a quote verifies only when every piece is found (never drop a piece; a short piece must be found too), the
  pieces occur in order within one line or a small window, and the number check runs on the matched document span
  rather than on the model's string.

### M2. The bank opener (the first line he reads aloud) is not grounded at all (medium, by reading)

- `brain/verse_brain/prep/prompt.py:26` tells the model the opener "must not state any number, date or name".
  `brain/verse_brain/prep/ground.py:166` only checks that it is not empty, and line 208 stores it as is. Points and
  `deep` go through `_check_text`; the opener does not, and it has no `src` lines by design.
- Effect: an opener with an invented figure passes into `bank.jsonl` and `pack.md` (`pack.py:65`, `SAY:`), and is the
  line the overlay shows first on a bank hit.
- Fix: in `_ground_bank`, reject or flag an opener for which `significant_numbers(opener)` is not empty or that
  contains a number not supported by the entry's verified sources; list those in `review.md`.

### M3. Network errors in the middle of a stream are not recognised as "offline" (medium, proven mapping)

- `brain/verse_brain/runtime/transport.py:155-158`: exceptions raised while iterating the SSE stream go through
  `map_sdk_error`. The SDK (anthropic 1.13.0, `_streaming.py`) does not wrap transport errors during iteration, so
  they arrive as raw `httpx2` exceptions, and `map_sdk_error` (lines 110-128) only knows the `anthropic.*` classes.
- Proof: `map_sdk_error(httpx2.ReadError("x"))`, `RemoteProtocolError` and `ReadTimeout` all return the generic
  `TransportError` (kind `error`), not `Offline`.
- Effect (`engine.py:1024-1047`): no `offline` status, no `pending_turn`, so the question is not re-answered when the
  connection returns; D is not retried (only `RateLimited`/`Overloaded` are, `engine.py:392`); the overlay gets a
  generic `error: ReadError`.
- Fix: map `httpx2.TransportError` and `httpx2.TimeoutException` (and their subclasses) to `Offline`.

### M4. The fast tier gets no second attempt on 5xx/overloaded (medium, by reading)

- `engine.py:199`: `retries_left` is 1 only for tiers D and A. `engine.py:392-400`: an F call that fails with
  `Overloaded` before any text is raised at once; `on_call_error` (`engine.py:1045-1047`) sends `status error`.
- Effect: one 529 on the Haiku call means the question gets no SAY line; D still fires (`_decide_d`,
  `engine.py:1636-1640`) with `opener=None`, 2 or more seconds later. With H1 this is the second place where an
  overloaded API is treated as a hard failure.
- Fix: for F (not S), when no text has been seen, retry once immediately on the other lane; hedging already has the
  second connection warm.

### M5. Date facts pass with the wrong year (medium, by reading)

- `brain/verse_brain/prep/ground.py:104-111`: a `date` value is accepted when either its 4-digit year or its last
  number appears in a quote (`any(...)`). Value `2025-03-14` with the quote `launched on 14 March 2024` passes on
  the `14`.
- The fact's text is number-checked separately, but the `value` field is what the chip shows.
- Fix: require every numeric part of the value that the quote could carry (year and day) to be present; `all`, not `any`.

### M6. A failed route or language swap ends the whole run (medium, by reading)

- `app/Sources/VerseTurns/VerseRunner.swift:517-526` and `609-613`: `cutOver` runs after the old pipeline has been
  stopped. When `p.next.start()` throws, it sets `listenFailed`, returns false and the loop does `break loop`, which
  ends the session. The automatic language switch (`VerseRunner.swift:592-597`) goes through the same path.
- `prepare()` ran earlier, so this needs a failure between prepare and start (device taken, permission revoked).
- Fix: on a failed start, restart the previous configuration (route and language of `old`) instead of ending.

### M7. PID-route tap rebuild can leave remote capture dead without any signal (medium-low, by reading)

- `app/Sources/VerseAudio/ProcessTapSource.swift:189-197`: `refreshPIDList` tears the tap down and calls `startTap`.
  If that throws, the result goes only into `refreshLog_`; `makeDescription` (line 99) has already stored the new
  object list, so the next notification with the same list returns early at line 192 and nothing retries.
- Also `tapFormatDescription`, `route` and `fallbackReason` are written from the control queue and read elsewhere
  without the lock.
- Fix: on failure restore `tappedObjects` to the old list (or schedule a retry), and surface it as a listen issue.

### L1. `_to_float` reads a three-decimal number as thousands (low, proven)

- `brain/verse_brain/prep/sources.py:37`: `numbers_in("0.125")` is `{125.0}` and `numbers_in("3.141 s")` is
  `{3141.0}`. Both sides of a comparison are parsed the same way, so the usual effect is nil; the wrong accept is a
  claim of `125` against a quote that says `0.125`.
- Fix: treat `0.xxx` and any group not preceded by 1-3 digits and followed by exactly three as a decimal; or decide
  by the note's language.

### L2. Commit handles match by prefix in both directions (low, by reading)

- `brain/verse_brain/prep/sources.py:129-134`: `ch.startswith(key) or key.startswith(ch)`. An empty or one-letter
  key (handle `commit:` or `a`) resolves to the first commit that matches. The quote must still be in that commit's
  line, so the effect is a wrong `ref`, not an unsupported claim.
- Fix: require a key of at least 7 hex characters.

### L3. `on_start` blocks the brain's input loop while it pre-warms (low, by reading)

- `engine.py:597-600` awaits `on_start` inside `handle`, and `__main__.py:172` awaits `handle` per line. For up to
  `prewarm_attempts * prewarm_attempt_s` = 36 s no other message is processed, including `control stop`.
- Today Swift waits for `ready` before it listens, so this matters mainly after a restart (the re-sent question
  waits behind the pre-warm) and when H1 is fixed with longer retries.
- Fix: run the pre-warm as a task (`_spawn`) and return from `on_start`.

## 2. Things checked that are fine

- The API key: read from the Keychain by the brain itself (`prep/keychain.py`), handed to the SDK clients, not
  logged; `transport.py` forwards no message text for 401/403 and keeps only rate-limit headers. `BrainProcess` never
  sees it. (How the app writes it is in section 3.)
- `anthropic` 1.13.0 exposes `APIStatusError.type`, so an `overloaded_error` event inside a 200 stream is mapped to
  `Overloaded` correctly (`transport.py:122`).
- Prep writes the session folder under a temporary name and renames it (`pipeline.py:329-346`); `summary.md` is
  written with a temp file and `os.replace` (`engine.py:2169-2173`).
- Cache breakpoints: one on the pack, one every 4 turns (`runtime/prompt.py:23,179-190`), inside the API's lookback.
- `Call.discard()` releases its waiters when the task is cancelled before its first step (`engine.py:240-254`).

## 3. Further findings from the delegated passes

Three Opus sub-reviews covered `VerseSpeech` + `VerseMeet` + meeting coordination; the UI controllers, session
files, trash, memory service, Keychain and voice keys; and the secondary Python modules. Their three most severe
findings are H6-H8 above, which I re-read in the code (H7 re-run). The rest is listed here as reported; I spot-read
the lines of S1, S2, S4, U1, U3 and P1 and did not re-check the others.

Speech, meeting detection:

- **S1 (medium)** `VerseSpeech/ListenSession.swift:161-165,118`: when `start()` fails for the second pipeline, the
  catch only stops sources; engines stay claimed and `discardPrepared()` is a no-op because `started` is already
  true. Each failure leaves about 600 MB of Nemotron model claimed for the life of the process. Fix: cancel every
  built engine in the catch.
- **S2 (medium)** `VerseMeet/CalendarPrep.swift:43-66`, `VerseUI/MeetingCoordinator.swift:141,264-265`: dismissing
  "Preparing…" or quitting cancels only the Swift task. The detached task blocks on `readDataToEndOfFile()` and
  never terminates the Python prep, which goes on spending up to its budget and leaves an orphan session folder.
  Fix: `withTaskCancellationHandler` that calls `process.terminate()`.
- **S3 (medium, likely)** `VerseSpeech/AutoLanguage.swift:171-174,208-209,227`: a shadow final that arrives after
  its main final was judged (later than `pairGrace` 1.5 s) votes alone and can flip the call language after 6 s of
  speech. Not verified that a mismatched recognizer reaches the 0.6 score.
- **S4 (low-medium)** `VerseSpeech/SwitchingEngine.swift:194-196`: `abandonLoad()` is skipped when
  `apple.finish()` throws; the Nemotron lease is never released. Fix: `defer`.
- **S5 (low)** `VerseSpeech/NemotronModel.swift:27-28,85-90`: `unloadIdle()` is called only by the CLI
  (`verse-run/main.swift:157`); in the app, models of every swap stay resident (about 2.4 GB after one swap).
- **S6 (low, likely)** `VerseMeet/MeetingDetector.swift:18,96`: "Safari" is detected through
  `com.apple.WebKit.GPU`/`WebContent`, which every WKWebView app shares.
- **S7 (low)** `VerseSpeech/ShadowRecognizer.swift:157-181`: an engine prepared but failed at `start` is not
  cancelled, and any error excludes the language for the rest of the call.
- **S8 (low, not verified)** `VerseSpeech/ChannelPipeline.swift:94-100,121-124`: the silence pump fills zeros after
  150 ms without a chunk; with a high-latency input (Bluetooth) the real chunk that follows is trimmed.
- **S9 (low, not verified)** `VerseMeet/EventKitBackend.swift:7,26`: the event store is created before
  authorization and never reset when access is granted later.
- **S10 (low)** `VerseSpeech/ListenSession.swift:151-152,252-261`: the bleed-gate decision log grows for the whole
  call (every volatile `me` result).
- **S11 (low, likely)** `VerseUI/MeetingCoordinator.swift:195-196`: a dismissed meeting prompt is keyed on the input
  start time and returns when the app's mic input pauses for 10 s.

UI, session files, secrets:

- **U1 (medium)** `VerseUI/FileLog.swift:38-39`: `seekToEndOfFile()` and `write(_:)` are the non-throwing FileHandle
  calls that raise an Objective-C exception on an I/O error. A full disk during a meeting crashes the app on the
  next log line (every brain stderr line goes through here). Fix: `try h.seekToEnd()` / `try h.write(contentsOf:)`.
- **U2 (medium, likely)** `VerseVoice/AppleVoice.swift:120,151-157`: a stale `didCancel`/`didFinish` callback
  resumes the next utterance's waiter. In a practice interview, Skip or Repeat makes the new line count as spoken at
  once, the mic opens while the voice still talks, and the interviewer's audio is transcribed as the answer.
- **U3 (low-medium)** `VerseUI/KeychainStore.swift:52-56`, `VerseVoice/VoiceKeys.swift:63-67`: a save is confirmed
  by "an item exists", not by the new value. If `-U` fails to update, Settings says saved and the old key stays.
  Fix: compare the stored last-4 comment with the new key.
- **U4 (low-medium)** `VerseUI/VerseController.swift:586-589`: Retry on the error panel always calls `start()`
  (prepared session, meeting route), also after a failed Start-now or room session.
- **U5 (low-medium, likely)** `VerseUI/ConversationPrep.swift:154-156,165,172-175`, `VerseUI/MeModel.swift:326-328`:
  readability handlers are removed 50 ms after exit, so the last stdout line (the session folder) can be lost; a
  `cancel()` before `process.run()` does nothing and the spend is then not recorded.
- **U6 (low)** `VersePosting/PostingFetcher.swift:35-44,57,151-152`: any http(s) host is fetched, including
  loopback and link-local addresses and redirects to them, and the whole body is downloaded before the 3 MB cap.
- **U7 (low)** `VerseUI/EntityStore.swift:478-486`, `VerseUI/SessionTrash.swift:277-280`: undo of Move to Trash does
  not restore the session's person/company links once any commit has pruned them.
- **U8 (low)** `VerseUI/GeneralPrep.swift:25-31`, `VerseUI/QuickStart.swift:157-160`: `seed` returns true when the
  copy failed, so the ad-hoc folder gets no `pack.md` and the run fails at start.
- **U9 (low, likely)** `VerseUI/TranscriptDocument.swift:120`, `VerseUI/ChatLog.swift:100`: strict UTF-8 decoding of
  the whole file returns nil when a writer is mid-character; the chat then loads empty and question ids restart at
  `q1`, which attaches new answers to old turns.
- **U10 (low)** `VerseUI/MemoryService.swift:82,509-510`: the session being recorded is left out of the manifest but
